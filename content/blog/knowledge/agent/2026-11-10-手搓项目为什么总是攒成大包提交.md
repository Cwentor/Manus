> **一句话结论**：大包提交的根因不是懒，而是把「业务验证的时钟」和「代码提交的时钟」绑在了一起。功能跑通才提交，等于让提交粒度和功能粒度强制对齐；而功能粒度天然是一周到一个月。想拆开，只需要做两件事：**把责任边界在开工前物化**，**让每次提交只承载一个可独立回滚的意图**。

---

## 一、先把现象说准：大包提交到底长什么样

一次典型的大包提交，通常是这样的：几十个文件、上千行 diff、commit message 写着 `feat: 完成用户中心模块`。点开看，里面混着新建目录、改表结构、接口签名调整、三个页面的实现、两个顺手修的老 bug、一次全局格式化，还有一行忘了删的 `console.log`。

这种提交有个共同特征：**它不是一个提交，是一个阶段的快照**。

区别在于：

| | 原子提交 | 阶段快照提交 |
|---|---|---|
| 回答的问题 | 我改了什么意图 | 我这段时间干了什么活 |
| 回滚代价 | 局部，可控 | 全局，等于回退工期 |
| Review 可行性 | 能逐条判断对错 | 只能判断"看起来跑得通" |
| 出问题时 | `git bisect` 定位到行 | 只能靠人回忆 |

阶段快照提交的真实成本不在提交那一刻，在于它之后的三件事上：review 失效、回滚不敢做、故障无法归因。而这三件事，恰好是工程效率的地基。

---

## 二、根因：两个时钟被绑死了

### 2.1 两种时间尺度本来就不同

- **业务验证的时钟**：一个功能要跑通、要被人点一遍、要在真实数据上不炸——以天、周为单位。
- **代码提交的时钟**：一段逻辑闭环了、一个契约定下来了、一个 bug 修完了——以分钟、小时为单位。

正常工程里，两者独立运行：提交跟着逻辑走，验证跟着业务走，中间用分支、开关、灰度隔开。

手搓项目（尤其是人 + Agent 一起手搓）最容易犯的错，是把提交当成"验证通过的仪式"：**没跑通不敢提交，跑通了才敢提交**。这个信念在单人小脚本里是对的，在真实项目里是灾难。

因为它隐含了一个错误前提：**提交 = 交付**。提交其实只是"存档 + 说明意图"，交付才需要验证通过。

### 2.2 为什么手搓会放大这个问题

手搓 + Agent 协作的结构性特征是：**代码的产出速度远大于验证速度**。

Agent 十分钟能铺出五个文件的骨架，人验证这五个文件的行为正确性可能要两小时。这中间的巨大缺口，只能由"未提交的工作区"来缓冲。工作区于是从"临时暂存"变成了"实际的主存储"。

一旦工作区成了主存储，会发生三件连锁反应：

1. **不敢提交**——提交就意味着承认这些代码"有资格进历史"，而它们还没被验证。
2. **越攒越大**——缓冲区的容量只增不减，因为验证始终追不上产出。
3. **认知绑定**——等终于跑通，这些改动在脑子里已经是一个整体了，拆分反而要额外做一次"回忆 + 分类"的脑力劳动。

第 3 点是最隐蔽的。人不是不愿意拆，是拆的成本在跑通那一刻最高——你刚把所有东西捏成一个能跑的形态，让你拆开，心理上像拆自己刚搭好的乐高。

### 2.3 「以功能阶段为周期攻坚」的必然结果

所以，以功能阶段和业务验证为周期的攻坚，产出大包提交不是意外，是**结构决定的必然结果**：

```
功能阶段开始 ────────────────────────► 业务验证通过
    │                                        │
    └──── 所有改动都悬在工作区 ──────────────┘
                                             │
                                    一次性打包提交
```

这个周期的每一环都在推动"攒"：任务颗粒度大 → 中间没有验收点 → 没有可提交的逻辑边界 → 只能整体打包。

**要改的从来不是最后那一下 `git add .`，是前面的任务颗粒度。**

## 三、拆开看：一个大包里混了五种东西

把典型的大包提交拆解，里面的改动其实是五类不同的东西，它们的 review 关注点、回滚代价、出错概率完全不同：

| 类型 | 例子 | 该独立提交吗 | 混进去的代价 |
|---|---|---|---|
| **结构迁移** | 新建目录、移动文件、重命名、批量格式化 | 必须，且单独 | diff 被噪音淹没，真实改动看不见 |
| **契约变更** | 表结构、类型定义、接口签名、事件字段 | 必须，且靠前 | 回滚时连带炸掉调用方 |
| **逻辑实现** | 业务规则、算法、状态流转 | 应该，按数据流切片 | 无法单独回滚某个规则 |
| **边界修补** | 顺手修的旧 bug、兼容分支 | 应该，最该单独 | 出问题时说不清是新代码还是老修复引发 |
| **噪音** | 调试日志、注释掉的代码、依赖版本漂移 | 不该存在 | 污染 diff，制造 review 疲劳 |

一条实用经验：**如果一次提交同时包含"结构迁移"和"逻辑实现"，那它一定没法 review。** 因为 review 者要在移动过的文件里找真实改动，找着找着就放弃了，最后只回一句 LGTM。

## 四、责任边界：骨架归 AO，血肉归人

边界不清的协作，表现为一种典型的疲劳：双方都在改，都在改得对，但合起来不对，且说不清是谁的责任。

解决方式不是"多沟通"，是**在开工前把边界写下来、变成物**。

### 4.1 AO 的交付物是骨架，不是功能

AO 在这个协作模型里负责"代码基础骨架"。这里的关键认知是：**骨架的验收标准不是"能跑"，是"能被填写、能被验证"**。

一份合格的骨架应该交付这五样：

1. **目录与文件归属**——哪些文件是本次要动的，哪些是共用的，哪些不许碰。
2. **接口契约**——类型定义、函数签名、数据结构、API 出入参。契约是边界的可执行形态。
3. **数据流路径**——数据从哪进来、经过哪些节点、落到哪里。每个节点都要能指出来。
4. **最小可运行闭环**（walking skeleton）——一个从入口到出口、全是假数据但链路通的版本。它证明骨架是活的，不是一堆空文件。
5. **边界声明**——本次允许改动的路径白名单，以及"这些文件归你，那些归我"的明确切分。

骨架交付的价值在于：**它把"要不要改这个文件"从判断题变成了查询题。**

### 4.2 人的交付物是三件事

人不是"填代码的"，人在这套分工里承担的是三件不可外包的职责：

- **执行构建**：把骨架填成真实业务逻辑。这部分可以和 Agent 交替做，但最终的正确性判断在人。
- **预定边界**：在开工前把范围、验收标准、禁止项定下来。**边界写在开工前，不是写在冲突后。** 事后划边界，本质是追责，不是协作。
- **验证数据流**：不是"点一遍看页面对不对"，而是沿着数据流逐节点确认——输入是什么形态、变换后是什么形态、落库/落盘是什么形态、每个环节能不能观测到。数据流验证通过，功能正确性才有地基。

### 4.3 对照表

| 维度 | AO（骨架侧） | 人（构建与验证侧） |
|---|---|---|
| 交付物 | 结构、契约、数据流路径、可运行闭环 | 真实业务逻辑、范围定义、验证结论 |
| 决策 | 怎么组织代码 | 做什么、做到什么程度算完 |
| 验收标准 | 契约可被填写、链路可被观测 | 数据流每个节点符合预期 |
| 不该做 | 替人决定业务规则、顺手改无关文件 | 边界的口头化、验证的抽样化 |
| 典型越界 | 为"顺手优化"改了共用模块 | 改了契约没同步，让骨架失效 |

### 4.4 三个越界症状，出现就该停下来

1. **同一段代码被两方先后"优化"**——说明归属没定，或者定了没物化。
2. **改动落在白名单之外**——不是能力问题，是边界声明不够硬，或者根本没声明。
3. **Review 时说不清某行为什么被改**——契约没成为唯一事实源，双方各有一份心里的事实。

### 4.5 把边界变成物，而不是变成话

口头约定在压力下最先失效。能扛住压力的边界，都是写进文件里的：

- 任务单里列出**允许改动的路径清单**，超出即视为范围变更，需要重新确认。
- 共用模块用 **CODEOWNERS** 或显式的"改动需确认"标注。
- 契约用可执行的形式固化：类型文件、JSON Schema、fixture / mock 数据。**mock 是契约的可执行版本**，比文档可靠。
- 一次任务一个分支，分支名带上任务标识，让"这次改了什么"在 Git 里有天然边界。

## 五、原子提交：判定标准

原子提交不是"越小的提交越好"。切得过碎（一个提交改一行）同样有害，因为它破坏了意图的完整性。

原子提交的定义是：**一个提交 = 一个可独立解释、可独立回滚、可独立验证的意图。**

三条硬标准，缺一不可：

1. **一句话能说清，且这句话里没有"和"。**
   - ✅ `fix: 修正分页偏移量在多页场景下的越界`
   - ❌ `fix: 修正分页 bug 和调整列表样式`
   - 只要你想用"顺便""同时""以及"，就说明该拆。

2. **单独回滚它，不会伤到别的功能。**
   - 反例：一次提交里同时改了数据结构和读取逻辑，回滚任一半都会让另一半崩掉。
   - 这条标准实际上在逼你先提交契约、再提交实现——契约和实现在回滚意义上是两个意图。

3. **单独 checkout 这个提交，项目能构建、测试能过。**
   - 做不到这条，说明你的提交依赖了未提交的东西，或者依赖了后续提交。两种情况都意味着拆分切错了位置。

一条加分项：**commit message 写"为什么"，不写"做了什么"。** 做了什么，diff 会说；为什么这么做、放弃了哪些方案，只有你知道，且三个月后只有这份 message 记得。

## 六、拆分手法：五种能立刻用的

### 6.1 结构改动先单独提交

移动文件、重命名、批量格式化、升级依赖——这些没有任何行为变化，全部单独一个提交，message 写 `refactor: 将 xxx 目录迁移至 yyy，无行为变更`。

好处是接下来所有行为改动的 diff 都是干净的。这一点在 Agent 参与的协作里尤其重要：**Agent 最爱的就是顺手整理结构**，如果不先隔离，真实改动会被彻底淹没。

### 6.2 按数据流分层拆

一个功能天然有方向：数据从外到内、从下到上。按这个顺序拆提交：

```
契约/类型  →  纯逻辑/纯函数  →  适配层（IO、接口、存储）  →  调用方/UI
```

这个顺序的好处是每个提交都建立在前一个已成立的基础上，回滚也可以从外层往回剥。反过来（先写 UI，再补接口，最后定类型）几乎必然产出大包，因为每一步都在猜下一步。

### 6.3 用分块暂存替代 `git add .`

`git add .` 是攒大包的加速器。把工作区一次性全部纳入，等于宣告"这些改动是同一个意图"——而你根本没有做过这个判断。

用 `git add -p` 逐块确认，或按路径精确 add。多任务并行时（改 A 功能时顺手碰了 B），这是唯一可靠的隔离手段。

一条纪律：**`git add .` 只在你能一句话说出"这些改动属于同一个意图"时才允许。**

### 6.4 未验证的代码用开关隔离，不用"不提交"隔离

这是解开两个时钟的关键手法。

业务验证还没做，不代表代码不能进历史。用 feature flag、配置开关、独立分支把它隔在生效范围之外：

```js
// 未验证的新链路：代码已合入，行为默认关闭
if (flags.newPaymentFlow) {
  return newFlow(payload); // 业务验证通过后再默认开启
}
return legacyFlow(payload);
```

这样提交和验证就解绑了：提交按时发生，验证按周发生，两者不再互相绑架。分支是更重的版本，开关是更轻的版本，按功能的爆炸半径选。

### 6.5 每个提交保持绿

"能构建"是底线，不是目标。一个不能构建的提交，会把 `git bisect` 变成抽奖。

如果确实需要 WIP 提交（比如临时抢救现场），在 message 里显式标记 `wip:`，并且合并前必须整理成意图提交。**WIP 提交属于私有分支，不属于主干历史。**

## 七、让规则不依赖自觉：三道机制

只靠"下次注意"的规范，一定会退化。要么进流程，要么进工具。

### 7.1 任务颗粒度决定提交颗粒度（根因层）

想提交小，先让任务小。把"功能阶段"切成"数据流切片"，每个切片自带一个验收点：

| 阶段划分方式 | 示例 | 产出 |
|---|---|---|
| 按功能 | 「完成用户中心」 | 一个大包 |
| 按数据流切片 | 「用户数据落库 + 读回来一致」 | 2~3 个原子提交 |
| | 「列表分页正确」 | 1~2 个原子提交 |
| | 「权限过滤生效」 | 1~2 个原子提交 |

切片的判定标准很简单：**一个切片能被单独验证，且验证它不需要等其他部分完成。** 能被单独验证的东西，天然能被单独提交。

这是所有改进里性价比最高的一条。任务颗粒度不改，其他手法都只是补救。

### 7.2 提交前的规模门禁（工具层）

在 pre-commit 或 CI 上加两道软性门禁：

- 单次提交改动文件数超过阈值（比如 8 个非 lock 文件）→ 提示并要求说明理由。
- 提交内容命中调试残留（`console.log`、`debugger`、`print(`）→ 阻断。

门禁的目的不是完美拦截，是**制造一次停顿**。大包提交往往发生在无意识的连续操作里，一次停顿足以让人醒过来。

### 7.3 每日绿色提交（节奏层）

硬性节奏：**每个工作日至少产生一次"能构建的提交"**。

它的意义不在提交了多少，而在建立一个心理事实：工作区不是主存储，Git 历史才是。一旦这个习惯成立，工作区里的未提交内容就自然变少了，因为每天结束时它会被清空一次。

这也是解绑时钟的日常版本：不要求验证通过，只要求逻辑闭环。

## 八、检查清单

**开工前（4 问）**

1. 这次的改动范围，路径清单写下来了吗？
2. 哪些是 AO 的骨架产出，哪些是人的构建产出？分界在哪？
3. 这个任务能切成几个可单独验证的切片？每个切片对应几次提交？
4. 验收标准是行为描述，还是"跑通了"这种感受描述？

**提交前（5 问）**

1. 能用一句话说清这个提交的意图吗？句子里有"和"吗？
2. 单独回滚它，会不会弄坏别的功能？
3. 单独 checkout 它，能构建吗？
4. 里面有没有混进结构迁移、格式化和调试残留？
5. message 里写了"为什么"吗？

**每周回看（2 问）**

1. 最大的那个提交有多少行？它本来应该拆成几个？
2. 拆分失败的原因是任务太大，还是拆分手法不熟？

## 九、最后一句

大包提交看起来是个 Git 习惯问题，实际上是**协作节奏和边界定义的外在症状**。

AO 交出可被填写的骨架，人负责构建、划界与验证数据流——这套分工成立的前提是边界在开工前就被写成了物。而原子提交，是这套分工在 Git 历史里留下的、可被检验的证据。

节奏改了，颗粒度自然会变；颗粒度变了，提交自然会小。反过来先逼着自己拆大包，通常撑不过两个迭代。
